Manual Bank Transfer — Jira-ready stories

Epic allocation: use existing CRP-250 for Manual Bank Transfer, preserving its existing implementation tickets and history. This documentation proposes that title/scope; it does not rename Jira itself.

This set contains 30 stories. It owns Manual Bank delivery and the shared venue screens, Save/Cancel, destination-recording foundation, cash-only path, bank draft flow and shared review presentation. Cheque adds its own fields and behaviours through dependency links. The Manual Bank accelerator can ship before the full selector, which is owned by the Cheque epic.

Exports contain exactly one venue within one client. CSV headings can be renamed in Strapi; all eight columns remain in fixed order. Export dates use the selected venue’s timezone. First export checks the current venue wait and completes valid included payouts; repeat downloads update Last Exported DateTime without repeating completion. Manual Bank remains excluded from automated execution and automated daily spending.

MBT-01 — Open the shared venue settings screen as an Admin

Epic: Manual Bank Transfer — CRP-250

Jira placement: New — shared Admin venue screen owned by Manual Bank; reuse CRP-314 configuration

Previous combined reference: replaces JUS-01.

User story: As an Admin, I want to open payout destination settings for a venue I manage, so that I can configure its Manual Bank process and use the same screen as other destinations are delivered.

UI description: From the Admin venue management area, open a permitted venue and its Payout Destinations section. Show the venue name and saved Manual Bank settings.

Acceptance criteria:

  • The Admin can view and edit Manual Bank Transfer Enabled and Venue Code for venues they are permitted to manage.
  • The selected venue is clear before editing or saving. Changes affect that venue only.
  • An Admin cannot configure another client’s venues or access Super Admin global configuration.
  • Users without configuration permission cannot save venue settings through the screen or a direct request.
  • Saved values agree with the Super Admin and Strapi venue screens. CSV heading controls remain in Strapi under MBT-26 and MBT-27.
  • This epic owns the shared screen and permission behaviour. CHE-01 and CHE-02 add Cheque Enabled and cheque collection mode to this same section when Cheque is delivered.

MBT-19 — Filter exports by collection-date range

Epic: Manual Bank Transfer — CRP-250

Jira placement: Existing CRP-310 and CRP-311 — retain Jira date-range behaviour

Previous combined reference: replaces JUS-41.

User story: As an Authoriser, Admin or Super Admin, I want to export manual payouts within a collection-date range, so that I can prepare or retrieve the relevant file.

UI description: Collection-date range shows Start Date, End Date, one selected venue, its timezone, matching payout rows, count and Download CSV. Label rows Ready for first export, Held or Already exported; show Last Exported DateTime for previously exported records.

Acceptance criteria:

  • Filter using recorded winning date/time, which is the source of Collection DateTime in this export.
  • Include eligible unexported payouts and previously exported/completed manual payouts from that selected venue within the range.
  • Invalid ranges show validation; a valid range with no exportable rows shows a clear empty result.
  • Interpret Start Date and End Date in the payout venue’s saved timezone. Include payouts from local midnight at the start date up to, but not including, local midnight on the day after the end date.
  • Use the selected venue’s correct daylight-saving offset at each date boundary. Export one venue at a time.
  • Previously exported rows do not need to serve another waiting period; newly exported rows must satisfy first-export conditions.
  • Clearly distinguish new-export rows from Already exported rows before confirmation; users can identify when the date-range file will download existing records again.

Confirmed rule / scope note: D1 confirmed — use the venue’s timezone for inclusive date bounds. This uses the existing Jira collection-date mode rather than the earlier export-date-only tab.

MBT-20 — See ready, held, exported and skipped payout records

Epic: Manual Bank Transfer — CRP-250

Jira placement: Existing CRP-310 and CRP-311 — required before/after export visibility

Previous combined reference: replaces JUS-42.

User story: As an Authoriser, Admin or Super Admin, I want to see which payouts will export, which were exported and which were excluded, so that I can resolve issues and avoid accidentally downloading already exported records as new payouts.

UI description: Before export, show Ready for first export and Held payout lists with IDs and amounts; Held includes the reason. In date-range mode also show Already exported rows and Last Exported DateTime. After export, show included and skipped record lists with counts, IDs and outcomes.

Acceptance criteria:

  • Before download, identify eligible unexported records individually as Ready for first export. List held records separately with reasons such as Awaiting authorisation, Time delay remaining, Missing venue code or Required bank data missing.
  • After download, show exactly which payout IDs were included, distinguishing Newly exported from Downloaded again for previously exported rows.
  • Show skipped payout IDs, amounts and reasons alongside the successful rows; counts agree with the individual result lists.
  • Held and skipped payouts are excluded from CSV rows and are not completed by that export.
  • Failures to retrieve bank details or missing required values explain which payout needs attention.
  • Valid rows can still export when other rows are skipped; required missing data is never guessed.
  • Only show payout IDs and reasons within the user’s permitted client and venues.
  • Refreshing eligibility or fixing data updates the results without itself completing the payout.
  • On later visits, saved export status and Last Exported DateTime identify previously exported records. All unexported excludes them; date-range results visibly label them Already exported.
  • Date-range downloading of an already exported row is intentional and does not complete it again or resend its completion confirmation.

Confirmed rule / scope note: D9 confirmed — show individual ready/held records before export, included/skipped records after export and saved already-exported status on later visits.
